## Follow-up 2: import-recovery boundaries A and B (after candidate `abe0ebb`)
A bounded review of `abe0ebb` accepted FU1–FU5. It found two more failure boundaries in the same import/checkpoint recovery contract. Both are fixed in local commit `2efbdae`.

**Before evidence:** `tests/test_v031_recovery.py` uses only interfaces that also exist in `abe0ebb`, and was run unchanged in a worktree of `abe0ebb`. Assertions inspect persisted state through a newly opened `Store`. Result on `abe0ebb`: **8 of 10 failed**, every one on persisted state:
- **A (3 tests):** an input persisted as `status=imported, active=0` with counts populated, never superseded. In the manual reprocess case the replacement revision is stuck in that state.

  - with appended data, 5 occurrences instead of 3: `shared@0` and `r1@91` twice;

Two cases passed on `abe0ebb` as expected: the recovery that uses the same budget as the original delivery, which is the control case, and the upgrade-classification test, which only exercises the new column. All 10 pass on the corrected code.
